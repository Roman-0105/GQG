# GQS — контекст для Claude Code

Этот файл читается Claude Code автоматически при открытии проекта.
Здесь — сжатая история решений, чтобы не переспрашивать заново то, что
уже обсуждено и сделано.

## Что это за платформа

Веб-платформа (PWA) для учёта буровых работ и описания керна геологоразведочной
компании. Работает на ПК и смартфонах (Android/iPhone), с прицелом на офлайн-режим
в будущем (сотрудники в поле, слабая связь).

## Стек и архитектура

- **Frontend**: React + TypeScript + Vite, без своего backend-сервера
- **Backend**: Supabase (Postgres + Auth), доступ с фронтенда только через
  **publishable key** (безопасно светить в браузере) — **secret/service_role
  ключи в проект никогда не добавлялись и не должны добавляться**, вся
  защита данных — через RLS-политики в базе, а не через сокрытие кнопок в UI
- **Хостинг**: GitHub Pages (чисто статический — отсюда `HashRouter` вместо
  `BrowserRouter`, см. `src/main.tsx`), деплой через GitHub Actions при пуше в `main`
- **Миграции БД**: `supabase/migrations/*.sql`, применяются вручную через
  Supabase SQL Editor (копипаста), не через Supabase CLI — см. `supabase/README.md`

## Роли и права (см. ТЗ ниже, раздел 2)

Три роли: `general_director`, `technical_director` (права идентичны гендиру
везде), `party_chief` (начальник буровой партии/бригадир). Роль хранится в
таблице `profiles`, 1:1 с `auth.users`. Функция `is_management()` в БД
используется во всех RLS-политиках.

**Важно**: первого пользователя (гендира) создать через приложение нельзя —
курица-яйцо с RLS. Bootstrap только через SQL, см. `supabase/README.md`.
Дальше новых пользователей можно создавать через раздел "Пользователи" в UI.

## Ключевые решения, которые НЕ надо пересматривать без явного запроса

- **Бригадир = поле, выбираемое вручную** на каждом задании из списка
  пользователей с ролью `party_chief` (не привязан автоматически к участку) —
  сознательно так, после обсуждения с заказчиком
- **Задание "Описание керна"** может быть привязано к своей скважине
  (`drilling_task_id`) ИЛИ к скважине подрядчика (`external_*` поля, без
  персонала — у подрядчика свой персонал). Для скважины подрядчика обязателен
  `assigned_party_chief_id` — кто-то должен вносить сводки, а foreman там
  взять неоткуда
- **Суточная сводка НЕ хранится отдельно** — она считается на фронтенде как
  агрегация посменных сводок за дату. Только посменные сводки — реальные
  строки в таблице `reports`
- **Сводка при отправке всегда проходит через draft**: RLS на `report_costs`
  разрешает запись затрат только пока сводка `draft`, поэтому даже при "отправить
  на согласование" сначала сохраняем как draft + затраты, и только потом
  отдельным запросом меняем `approval_status` на `submitted` — см.
  `src/routes/reports/DailyReportForm.tsx`, там подробный комментарий про баг,
  который так чинили
- **При отклонении сводки** (`approval_status = 'rejected'`) автоматически
  ставится `edit_unlocked = true` — автор сразу может исправить и отправить
  заново, без отдельного запроса на правку через гендира
- **Экспорт — только .xlsx** (через SheetJS, `src/lib/xlsxExport.ts`), с
  **ленивой загрузкой** (`import()`) — библиотека тяжёлая (~300 КБ), не должна
  грузиться на каждой странице
- **Дизайн**: тёплая каменно-песочная палитра + мшисто-зелёный акцент
  (предметная область — керн/порода, не дефолтный SaaS-синий), шрифт Manrope
  self-hosted (не Google Fonts CDN — важно для офлайн-режима). Токены — в
  `src/index.css`. Не возвращать дефолтные цвета Vite-шаблона

## Не реализовано (сознательно отложено, не путать с "забыли")

- **Офлайн-режим** (IndexedDB, очередь синхронизации) — самая трудоёмкая
  часть, отдельный будущий этап
- **Табель** — структура не определена, заказчик отложил вопрос
- Управление справочниками (организации-подрядчики, категории затрат) —
  сейчас правятся только через SQL/Table Editor в Supabase напрямую, экрана
  в UI нет
- Редактирование уже созданных участков/заданий (кроме сводок) — есть только
  создание

## Workflow

- Ветка на фичу → PR → **обязательно `npm run build` и `npx tsc --noEmit`
  перед коммитом** → описание PR по-русски, подробное, с объяснением "почему",
  не только "что"
- Если PR меняет `supabase/migrations/` — миграцию нужно ОТДЕЛЬНО применить
  в Supabase SQL Editor (владелец проекта делает это вручную, скопировав SQL)
  — само по себе она не применяется автоматически нигде
- Полное ТЗ (все версии решений, включая отклонённые варианты и почему) —
  в истории переписки с заказчиком в claude.ai, не продублировано в репозитории
  файлом. Если нужны детали, которых нет в этом файле — переспросить заказчика,
  не додумывать самостоятельно
