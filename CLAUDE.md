# GQS — контекст для Claude Code

Этот файл читается Claude Code автоматически при открытии проекта.
Здесь — сжатая история решений, чтобы не переспрашивать заново то, что
уже обсуждено и сделано.

## Что это за платформа

Веб-платформа (PWA) для учёта буровых работ и описания керна геологоразведочной
компании. Работает на ПК и смартфонах (Android/iPhone), с прицелом на офлайн-режим
в будущем (сотрудники в поле, слабая связь).

## Стек и архитектура

- **Frontend**: React + TypeScript + Vite, без своего backend-сервера
- **Backend**: Supabase (Postgres + Auth), доступ с фронтенда только через
  **publishable key** (безопасно светить в браузере) — **secret/service_role
  ключи в проект никогда не добавлялись и не должны добавляться**, вся
  защита данных — через RLS-политики в базе, а не через сокрытие кнопок в UI
- **Хостинг**: GitHub Pages (чисто статический — отсюда `HashRouter` вместо
  `BrowserRouter`, см. `src/main.tsx`), деплой через GitHub Actions при пуше в `main`
- **Миграции БД**: `supabase/migrations/*.sql`, применяются вручную через
  Supabase SQL Editor (копипаста), не через Supabase CLI — см. `supabase/README.md`

## Роли и права (см. ТЗ ниже, раздел 2)

Три роли: `general_director`, `technical_director` (права идентичны гендиру
везде), `party_chief` (начальник буровой партии/бригадир). Роль хранится в
таблице `profiles`, 1:1 с `auth.users`. Функция `is_management()` в БД
используется во всех RLS-политиках.

**Важно**: первого пользователя (гендира) создать через приложение нельзя —
курица-яйцо с RLS. Bootstrap только через SQL, см. `supabase/README.md`.
Дальше новых пользователей можно создавать через раздел "Пользователи" в UI.

## Ключевые решения, которые НЕ надо пересматривать без явного запроса

- **Бригадир = поле, выбираемое вручную** на каждом задании из списка
  пользователей с ролью `party_chief` (не привязан автоматически к участку) —
  сознательно так, после обсуждения с заказчиком
- **Задание "Описание керна"** может быть привязано к своей скважине
  (`drilling_task_id`) ИЛИ к скважине подрядчика (`external_*` поля, без
  персонала — у подрядчика свой персонал). Для скважины подрядчика обязателен
  `assigned_party_chief_id` — кто-то должен вносить сводки, а foreman там
  взять неоткуда
- **Суточная сводка НЕ хранится отдельно** — она считается на фронтенде как
  агрегация посменных сводок за дату. Только посменные сводки — реальные
  строки в таблице `reports`
- **Сводка при отправке всегда проходит через draft**: RLS на `report_costs`
  разрешает запись затрат только пока сводка `draft`, поэтому даже при "отправить
  на согласование" сначала сохраняем как draft + затраты, и только потом
  отдельным запросом меняем `approval_status` на `submitted` — см.
  `src/routes/reports/DailyReportForm.tsx`, там подробный комментарий про баг,
  который так чинили
- **При отклонении сводки** (`approval_status = 'rejected'`) автоматически
  ставится `edit_unlocked = true` — автор сразу может исправить и отправить
  заново, без отдельного запроса на правку через гендира
- **Экспорт — только .xlsx** (через SheetJS, `src/lib/xlsxExport.ts`), с
  **ленивой загрузкой** (`import()`) — библиотека тяжёлая (~300 КБ), не должна
  грузиться на каждой странице
- **Дизайн**: тёплая каменно-песочная палитра + мшисто-зелёный акцент
  (предметная область — керн/порода, не дефолтный SaaS-синий) — цвета
  зафиксированы, не менять без явного запроса. Токены — в `src/index.css`.
  Не возвращать дефолтные цвета Vite-шаблона
- **Редизайн 2026-09-17**: пара шрифтов вместо одного, все self-hosted через
  `@fontsource` (не Google Fonts CDN — важно для офлайн-режима): Fraunces на
  заголовках (характер "полевого дневника геолога"), Manrope в интерфейсе,
  JetBrains Mono на всех числах — глубины/проценты/даты/деньги (класс `.num`
  в `src/index.css`). Библиотеки — `framer-motion` (анимации, один "большой"
  момент — переход между страницами в `AppShell.tsx` — вместо разрозненных
  дёрганий) и `lucide-react` (иконки)
- **Оболочка приложения** — `src/components/layout/`: `TopNav` (верхнее меню,
  только ПК, >=768px) и `MobileHeader` + `BottomTabBar` (телефон, <768px) —
  переключаются медиа-запросом в CSS, не JS-детектом ширины. Пункты навигации
  и видимость по ролям — один источник `navItems.ts`, не дублировать в
  компонентах
- **План бурения — одно число (`planned_daily_meters`, м/сутки), не календарь
  по датам**. Накопительный план на дату считается на фронте как
  `min(planned_daily_meters × дней с начала, projected_depth)` — см.
  `src/routes/tasks/TaskDashboard.tsx`. Обсуждалось с заказчиком 17.09.2026:
  реальный план буровой задаётся как темп, а не разными числами на каждый
  день. Если практика покажет плавающий темп — тогда таблица план/дата, не раньше
- **План по керну/фотофиксации на дашборде задания — это `projected_depth`
  связанной скважины** (своей — через `drilling_task_id`, подрядчика — через
  `external_projected_depth`), отдельного поля плана у `core_description_tasks`
  нет: керн описывают вдоль того же ствола, второй план был бы дублем
- **`reports.shift_notes` — одно текстовое поле**, не отдельные "что сделано" /
  "что помешало" — бригадир пишет то и другое одним связным текстом (так
  описал заказчик пример: "5 из 10 по плану — потому что…")
- **Виды заданий (миграция 0007, 17.09.2026, из разбора реального отчёта
  заказчику) — 4 штуки, у каждого своя логика назначения ответственного**:
  `drilling_tasks`, `core_description_tasks`, `core_sawing_tasks`
  (распиловка), `sampling_tasks` (опробование). Единый список и подписи —
  `src/types/taskType.ts`, не заводить локальные `type TaskType = ...` по файлам.
  - **Геологическая vs геотехническая документация** — это ДВА отдельных
    `core_description_tasks` на одну скважину (`documentation_type`), не два
    числовых поля на одном — идут независимым темпом, может быть разный
    документатор
  - **Распиловка — только своя скважина**, ответственный НЕ назначается
    отдельно: всегда `foreman_id` связанного `drilling_task_id` (решение
    заказчика — тот же бригадир, что бурит). Смены называются "День"/"Ночь"
    в интерфейсе — это те же `shift_number` 1/2, просто другая подпись
  - **Опробование — ответственного назначают ЯВНО ВСЕГДА**, даже на своей
    скважине (в отличие от описания керна, где это обязательно только для
    скважины подрядчика) — это может быть отдельная бригада, не буровая.
    Метрики — `samples_taken`/`samples_submitted`, без смен вообще
- **Копирование сводки в WhatsApp** (`src/lib/whatsappMessage.ts`) — формат
  подогнан 1:1 под реальный внутренний отчёт заказчика (17.09.2026), не
  придуман: "Отчёт по бурению {ДД.ММ.ГГГГ}" / "Смена {N}" / пустая строка /
  "Скважина: …" / "Буровая установка: …" / "Глубина: {забой}" / "Проходка:
  {метраж смены}" / пустая строка / текст из "Что сделано за смену". Часы
  работы в это сообщение НЕ входят. Отчёт для заказчика (сводный по всем
  скважинам участка сразу) — отдельная, более крупная задача, сознательно
  отложена вторым этапом
- **`npx tsc --noEmit` не ловит всё** — этот проект собирается через `tsc -b`
  (project references, см. `npm run build`), и он строже: минимум один раз
  словил ошибку индексации `Record<TaskType, …>` значением `TaskType |
  undefined` из `useParams()`, которую `tsc --noEmit` пропустил. Перед
  коммитом — всегда `npm run build`, не только `--noEmit`
- **Двойной сабмит сводки (19.09.2026)** — `DailyReportForm.tsx` `handleSubmit`
  защищён синхронным `useRef`-флагом (`submittingRef`), а не только
  `disabled={submitting !== null}` на кнопке. Реальный баг: быстрый повторный
  тап (характерно на телефоне при пересдаче отклонённой сводки) успевает
  вызвать `handleSubmit` дважды ДО того, как React перерисует `disabled` —
  React-стейт обновляется асинхронно. Первый вызов доводит сводку до
  `submitted` (снимает `edit_unlocked`), второй параллельный вызов на этапе
  черновика делает `update().select().single()` по уже неэдитируемой (по RLS)
  строке → 0 строк → PostgREST `PGRST116` `"Cannot coerce the result to a
  single JSON object"`. Если увидите этот текст ошибки где-то ещё в проекте —
  ищите такой же паттерн (async-обработчик без синхронной защиты от повторного
  вызова), не RLS-политику
- **Правка заданий (17.09.2026)** — все 4 формы заданий (`*TaskForm.tsx`)
  теперь двойного назначения: `taskId` в URL (`/sites/:siteId/tasks/:type/:taskId/edit`)
  включает режим правки той же формой, что и создание — insert/update
  собираются как ДВА раздельных вызова с разными объектами полей (`status`
  только при update, `created_by` только при insert), не один объект с
  условным спредом в один `insert/update` через тернарник — так ловилась
  ошибка типов на границе union (`tsc -b` ловит, `--noEmit` иногда нет, см.
  выше). Диаметры при правке — снести старые строки и записать текущее
  состояние формы заново (тот же приём, что с затратами сводки)

## Не реализовано (сознательно отложено, не путать с "забыли")

- **Офлайн-режим** (IndexedDB, очередь синхронизации) — самая трудоёмкая
  часть, отдельный будущий этап
- **Табель** — структура не определена, заказчик отложил вопрос
- Управление справочниками (организации-подрядчики, категории затрат) —
  сейчас правятся только через SQL/Table Editor в Supabase напрямую, экрана
  в UI нет
- **Автогенерация сводного отчёта заказчику** (по всем скважинам/заданиям
  участка сразу, формат из переписки 17.09.2026) — сознательно вторым
  этапом, после того как схема заданий (распиловка/опробование/документация)
  обкатается на реальных данных

## Workflow

- Ветка на фичу → PR → **обязательно `npm run build` и `npx tsc --noEmit`
  перед коммитом** → описание PR по-русски, подробное, с объяснением "почему",
  не только "что"
- Если PR меняет `supabase/migrations/` — миграцию нужно ОТДЕЛЬНО применить
  в Supabase SQL Editor (владелец проекта делает это вручную, скопировав SQL)
  — само по себе она не применяется автоматически нигде
- Полное ТЗ (все версии решений, включая отклонённые варианты и почему) —
  в истории переписки с заказчиком в claude.ai, не продублировано в репозитории
  файлом. Если нужны детали, которых нет в этом файле — переспросить заказчика,
  не додумывать самостоятельно
