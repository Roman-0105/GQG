# КЕРН — платформа полевого учёта часов и расчёта зарплаты

> Рабочее название проекта. Свободно меняется на Этапе 00.
> Версия: v0.1 · Дата: 2026-09-05 · Статус: концепция → Этап 0
> Полная визуальная версия этого документа: см. опубликованный Artifact «КЕРН» в этой сессии Claude Code.

Компания предоставляет геологические, геотехнические и буровые работы.
Бригадир ежедневно вносит отработанные часы; платформа сама рассчитывает
зарплату по настраиваемым правилам. Система должна быть гибкой (настройка
без правки кода) и ролевой (каждый видит и делает только своё).

## 1. Цели платформы

- **Единый источник часов** — один способ внести время, от него зависят
  зарплата, аналитика и загрузка участка.
- **Настраиваемость без программиста** — ставки, надбавки, вахтовые правила
  и роли меняются владельцем через интерфейс.
- **Полевые условия — норма** — форма табеля работает офлайн, не теряет
  данные без связи.
- **Ролевая прозрачность** — бригадир видит свою бригаду, руководитель
  участка — свои объекты, владелец — всё.
- **Аналитика на любом срезе** — день / неделя / месяц / квартал / год /
  произвольный период.
- **Аудируемость** — каждое изменение табеля и ставки — с автором и
  временем; расчёт объясним, а не «чёрный ящик».

## 2. Ролевая модель

Роль = набор прав `(ресурс, действие, область видимости)`. Ниже — базовый
комплект; владелец собирает из тех же прав свои роли (например «мастер
вахты» — права бригадира сразу на несколько бригад).

| Роль | Доступ | Что делает | Область видимости |
|---|---|---|---|
| Владелец компании | Полный | Правила ЗП, роли, участки, вся финансовая аналитика | Вся компания |
| Администратор / HR | Управление | Сотрудники, должности, ставки, допуски | Вся компания |
| Руководитель участка | Оперативный | Бригады и табели своих объектов, второе согласование, бюджет vs факт | Назначенные участки |
| Бригадир | Ввод данных | Табель своей бригады, метраж, заметки, фото | Своя бригада |
| Расчётчик / бухгалтер | Финансы | Ставки, надбавки, запуск расчёта ЗП, авансы, экспорт | Вся компания, без правки табелей после блокировки |
| Работник (опц.) | Самообслуживание | Свои часы, расчётный лист, заявка на отпуск | Только свои данные |
| Аудитор | Только чтение | Журнал изменений, все данные без права правки | Вся компания |

## 3. Доменная модель

Административная иерархия:

```
Компания
 └─ Участок      (название, описание, координаты, клиент/договор,
                  тип: геология / геотехника / бурение / смешанный,
                  бюджет, статус)
     └─ Бригада  (бригадир, состав, вахтовый график)
         └─ Сотрудник (должность, тип занятости, базовая ставка,
                        допуски и сертификаты)
```

Сквозные сущности:

- **Табель** — дата, сотрудник, участок, бригада, вид работ (бурение /
  дежурство / переезд / ремонт / обучение / простой по погоде), часы
  (обычные / сверхурочные / ночные), метраж (м), статус (черновик →
  на согласовании → подтверждён → заблокирован).
- **Расчёт ЗП** — период, свод по сотрудникам из подтверждённых табелей,
  авансы и удержания, итог к выплате, экспорт, статус (черновик →
  проведён → закрыт).

## 4. Табели и расчёт зарплаты

Поток согласования:

1. Бригадир вносит часы за смену (часто офлайн, в поле).
2. Табель уходит на согласование руководителю участка.
3. Подтверждение или возврат на исправление с комментарием.
4. Период закрывается — блокировка от правок.
5. Автоматический расчёт зарплаты по формуле.

Из чего складывается ставка:

- базовая часовая ставка по должности, с переопределением по участку;
- коэффициент сверхурочных (напр. ×1.5 после 8 ч/смену);
- ночная и праздничная надбавка, %;
- надбавка за вахту / удалённость + суточные, ₽/день;
- сдельная премия за метраж бурения, ₽/м;
- удержания: налог, авансы, компенсация за технику.

Правила — конструктор с наследованием: по умолчанию на уровне компании,
переопределение на уровне участка, затем на уровне должности/сотрудника.
Расчётный лист показывает разбивку по каждой составляющей.

## 5. Аналитика

**Временные срезы:** день, неделя, месяц, квартал, год, произвольный
период, сравнение периодов.

**Разрезы:** участок, бригада, сотрудник, должность, вид работ,
клиент/объект.

**Метрики:** часы (обычные/сверхурочные/ночные), фонд оплаты труда,
стоимость метра бурения (₽/м), бюджет участка (план vs факт), явка и
отсутствия, незаполненные табели (алерты).

Дашборды — ролевые: один и тот же набор витрин, разная область видимости.

## 6. Полевые условия и офлайн-режим

- локальная очередь (IndexedDB) — табель пишется без интернета,
  синхронизируется при связи;
- необязательные фото и GPS-метка к записи для спорных случаев;
- заблокированный на сервере период всегда побеждает при конфликте;
  конфликтующие черновики — в очередь на ручную проверку бригадиром;
- напоминания, если табель не закрыт к концу смены.

## 7. Технологический стек (рекомендация, обсуждаемо)

| Слой | Рекомендация | Зачем |
|---|---|---|
| API / backend | NestJS (TypeScript) + PostgreSQL + Prisma | Сквозная типизация от БД до фронта |
| Веб-панель | React + Vite + Tailwind + shadcn/ui | Быстрая сборка дашбордов и админки |
| Полевое приложение | PWA на том же React, офлайн-очередь | Один код для веба и поля |
| Фоновые задачи | BullMQ + Redis | Расчёт ЗП по расписанию, напоминания |
| Аналитика | Агрегирующие таблицы + Recharts; опц. Metabase | Гибкие отчёты без кода под каждый запрос |
| Развёртывание | Docker Compose локально; сервер компании/VPS на проде | Совместимо с локальной разработкой |
| Тестирование | Vitest/Jest + Playwright | Прогоняются независимым QA-агентом |

Ролевая модель и логика расчёта ЗП от конкретного стека не зависят.

## 8. Команда агентов разработки

Разработка идёт локально в Claude Code — каждая зона ответственности
закреплена за отдельным именованным агентом (`.claude/agents/*.md`).
Тестировщик и специалист по безопасности не пишут код сами — иначе
некому будет поймать собственную ошибку.

| Агент | Файл | Зона ответственности |
|---|---|---|
| Архитектор | `.claude/agents/architect.md` | Декомпозиция этапов, ADR, целостность модели |
| Backend-инженер | `.claude/agents/backend-dev.md` | API, БД, интеграции |
| Frontend | `.claude/agents/frontend-dev.md` | Реализация экранов, офлайн-табель |

| Независимый тестировщик | `.claude/agents/qa-tester.md` | Тест-планы, юнит/e2e, баг-репорты |
| Безопасность | `.claude/agents/security-reviewer.md` | Модель угроз, аудит ролевой модели и зависимостей |

## 9. Дорожная карта по этапам

Сроки — грубая оценка для одной команды агентов, работающей
последовательно; при параллельной работе backend/frontend возможно ужатие.

| Этап | Срок | Содержание | Критерий готовности |
|---|---|---|---|
| 00. Фундамент | 1–2 нед | Роли и права, выбор стека, каркас репозитория, команда агентов, дизайн-система | Документ подписан, репозиторий и агенты настроены |
| 01. Ядро и авторизация | 2–3 нед | Компания/пользователи/роли, RBAC, CRUD участков и бригад | Владелец заводит участок, бригаду, сотрудника, назначает бригадира |
| 02. Табели и согласование | 2–3 нед | Офлайн-форма табеля, цепочка согласования, напоминания | Полный цикл «внёс → согласовано → заблокировано» на тестовом участке |
| 03. Расчёт зарплаты | 3–4 нед | Конструктор ставок, запуск расчёта, авансы/удержания, экспорт | Расчёт сходится с ручным расчётом бухгалтера |
| 04. Аналитика | 2–3 нед | Агрегация данных, ролевые дашборды, все срезы времени | Бюджет vs факт виден на всех срезах |
| 05. Проверка качества ✅ | 1–2 нед | Независимое тестирование, аудит безопасности, нагрузка, приёмка | Критичных находок не осталось — RBAC/scope (33 сценария), формулы ЗП (7 сценариев), нагрузка на расчёт ЗП (deadlock под конкурентностью найден и устранён) |
| 06. Пилот 🔧 | 2–4 нед в поле | Docker-развёртывание, бэкапы/восстановление, инструкции по ролям, закрытие блокеров (сброс пароля, тупик возврата табеля) готовы. Запуск на реальном участке/бригаде и обратная связь — впереди | Инфраструктура и документация готовы; сам пилот с реальными людьми не запущен |
| 07. Полный запуск + бэклог v2 | — | Раскатка на все участки; бэклог: техника, нативное приложение, портал клиента, 1С | — |

## 10. Открытые решения

Зафиксировать до конца Этапа 00 — каждый пункт меняет объём или порядок работ:

1. Регион и нормы трудового законодательства (вахтовый метод, нормы
   переработок и суточных).
2. Стек — Node/TypeScript (рекомендация) или предпочтительнее Python?
3. Нужно ли нативное мобильное приложение бригадиру, или PWA закрывает
   сценарий полностью?
4. Хостинг — полностью локальный сервер компании или VPS с доступом из
   поля?
5. Нужна ли интеграция с бухгалтерией (1С, банк для зарплатных
   перечислений) в первой версии?
6. Одна компания или закладывать мультитенантность на будущее (аренда
   другими подрядчиками)?
7. Удержание налога (НДФЛ и т.п.) при расчёте ЗП — вводить вручную
   бухгалтером на каждый расчёт (текущее решение, `docs/adr/0004`) или
   нужна формула/интеграция с бухгалтерией?
8. Чем по замыслу отличаются вахтовая/удалённая надбавка
   (`remoteBonusPct`, % от заработка) и суточные (`perDiemAmount`,
   фиксированная сумма в день) — сейчас это два независимых поля, риск
   задвоить компенсацию за один и тот же факт (см. `docs/adr/0004`).
9. Границы периода расчёта: спецификация (раздел 0 этого документа)
   описывает полуоткрытый интервал `[periodStart, periodEnd)`, а код
   (`PayrollCalcService`) и форма на фронтенде (`Payroll.tsx`) реально
   работают как `[periodStart, periodEnd]` (обе границы включительно) —
   найдено qa-tester на Этапе 05, практику это пока не ломает (UI и код
   согласованы между собой), но доку и код нужно явно свести к одному
   варианту.
10. `RateRulesService`/`PositionsService` не фильтруют список по scope
    пользователя (найдено security-review на Этапе 05) — сегодня не
    эксплуатируется, т.к. ни одной сидовой роли не назначено право на
    `rate-rule`/`position` с scope `own_sites`/`own_crew`, но при
    появлении такой роли (например, «расчётчик участка») это станет
    реальной утечкой. Фикс отложен как неблокирующий по решению
    пользователя от Этапа 04 («остальные вопросы — в доработки»).
11. Нельзя внести метраж бурения (`metersDrilled`) с реального экрана
    табеля — поле есть в API, в расчёте ЗП (`perMeterBonus`) и в
    аналитике, но не в `TimesheetForm.tsx` (найдено docs-writer на
    Этапе 06). Если у пилотной бригады есть сдельная премия за метраж —
    без этого поля её физически нечем начислить.
12. `appliedRules` (какое правило ЗП применилось к какой строке табеля)
    вычисляется в `PayrollCalcService`, но теряется до ответа API —
    `PayrollService.runPayroll()` в конце перечитывает расчёт из БД, а
    `appliedRules` там не персистится (найдено docs-writer на Этапе 06,
    комментарий в коде обещает обратное). Бухгалтер не может
    перепроверить разбивку по правилам, хотя раздел 4 плана явно этого
    требует.
13. `PayrollRun.status` практически всегда `draft` — нет эндпоинта для
    перехода в «проведён»/«закрыт» (найдено docs-writer на Этапе 06).
    Из трёх статусов модели данных (раздел 3) реализован по сути один.
14. `Payroll.tsx` не показывает форму для `deductions` (удержаний) —
    только для `advances` (авансов), хотя API принимает оба поля
    одинаково (найдено docs-writer на Этапе 06).
15. `Positions.tsx`/`RateRules.tsx` — только создание и список, без
    редактирования/удаления (найдено docs-writer на Этапе 06). При
    правиле «побеждает целиком» (`docs/payroll-formulas.md`, D1)
    невозможность подправить уже созданное правило — не мелочь.
16. Нет пути саморегистрации первой компании/владельца — единственный
    вход в свежую систему держится на демо-пользователе из сида
    (`owner@demo.kern`/`change-me-now`, найдено devops на Этапе 06).
    Перед реальным пилотом это нужно решить — как минимум сменить
    пароль (см. `POST /auth/change-password`, добавлено на Этапе 06),
    в идеале — сделать штатный способ завести первого владельца.
17. Навигация (`AppShell.tsx`, `NAV_SECTIONS`) и `Dashboard.tsx` не
    фильтруются по роли — пункты меню видны всем независимо от прав,
    хотя по клику сервер всё равно вернёт 403 (уже отмечено как
    заглушка в самом коде; зафиксировано docs-writer на Этапе 06 как
    источник путаницы для пилотных пользователей).
