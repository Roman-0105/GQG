## 0. Входные данные расчёта

Расчёт зарплаты выполняется для `PayrollRun (periodStart, periodEnd)` и
берёт **только** `Timesheet` со `status = "locked"`, где
`workDate ∈ [periodStart, periodEnd)`. Табели в любом другом статусе в
расчёт не участвуют — это гарантия, что расчёт не зависит от ещё
не согласованных данных.

Дополнительный внешний вход (не из БД, передаётся при запуске расчёта):

- `advanceDeductionByEmployee: Map<employeeId, Decimal>` — авансы,
  выданные вручную. См. раздел 4.9.
- `deductionsByEmployee: Map<employeeId, Decimal>` (опционально) — прочие
  удержания. См. раздел 4.8 — намеренно не формула, а вход.

Базовая часовая ставка сотрудника (используется во всех формулах ниже):

```
baseRate(employee) = employee.baseRateOverride ?? employee.position.baseHourlyRate
```

## 1. Выбор применимого RateRule

### 1.1 Единица применения — целиком строка табеля, не сотрудник и не период

`Timesheet.siteId` — собственное поле строки табеля (не выводится из
`crew.site`). Это значит, что в пределах одного периода один и тот же
сотрудник теоретически может иметь табели на разных участках (переезд
между объектами, временное усиление бригады). **Правило выбирается
отдельно для каждой locked-строки табеля**, а не один раз на сотрудника
за весь период. Суммы по составляющим (`baseAmount`, `nightAmount` и т.д.)
в `PayrollLine` — это сумма построчных величин за период.

### 1.2 Кандидаты

Для строки табеля `T` сотрудника `E`:

```
candidates = RateRule[] где
  companyId = E.companyId
  AND (siteId IS NULL OR siteId = T.siteId)
  AND (positionId IS NULL OR positionId = E.positionId)
```

### 1.3 Выбор победителя — **вся строка RateRule целиком**, не отдельные поля

Из `candidates` выбирается ровно одна строка `RateRule`, все её поля
(`nightShiftPct`, `holidayPct`, `remoteBonusPct`, `perDiemAmount`,
`perMeterBonus`) применяются вместе, как единый набор. Поля из
невыигравших правил **не используются**, даже если они более
специфичны для какого-то одного параметра.

Порядок сортировки кандидатов (первый в списке — победитель):

1. `priority` по убыванию (явный приоритет владельца — решающий фактор);
2. при равенстве `priority` — специфичность по убыванию, где
   специфичность = `(siteId != null ? 1 : 0) + (positionId != null ? 1 : 0)`
   (правило и для участка, и для должности специфичнее, чем только для
   одного из них, специфичнее, чем общее для компании);
3. при равенстве и приоритета, и специфичности — `createdAt` по убыванию
   (более новое правило побеждает), как детерминированный последний
   тай-брейк, чтобы результат не зависел от порядка выборки из БД.

Если `candidates` пуст (для компании не настроено вообще ни одного
подходящего правила, включая общий wildcard) — **это ошибка валидации,
блокирующая расчёт для этой строки**, а не молчаливое применение нулевых
надбавок. См. раздел 6 (рекомендация backend-dev).

> **Важное расхождение с текстом плана — см. раздел 5.1 «Решения,
> требующие подтверждения», пункт D1.** Раздел 4 плана описывает
> конструктор как «наследование… переопределение на уровне участка,
> затем на уровне должности» — формулировка предполагает **точечное**
> переопределение отдельных полей, а не замену всего набора надбавок
> целиком. Схема Prisma (`RateRule` — non-nullable поля с
> `@default(0)`) не позволяет отличить «явно задано 0» от «не задано,
> дефолт», поэтому пофилевое наследование в текущей схеме реализовать
> надёжно нельзя. Спецификация ниже использует «побеждает правило
> целиком» как единственный вариант, совместимый с текущей схемой, — см.
> сценарий Е (F) в разделе 3 и D1, где показана разница в деньгах между
> двумя трактовками.

## 2. Формулы по составляющим (на одну строку табеля `T`, победившее правило `R`)

Обозначения: `rate = baseRate(E)`, `mult = E.position.overtimeMultiplier`.

### 2.1 baseAmount

```
rowBase = T.regularHours × rate
```

### 2.2 overtimeAmount

```
rowOvertime = T.overtimeHours × rate × mult
```

### 2.3 nightAmount

```
rowNight = T.nightHours × rate × (R.nightShiftPct / 100)
```

Надбавка считается **от базовой ставки**, а не поверх
переработки/сверхурочного множителя, независимо от того, пересекаются ли
ночные часы со сверхурочными. Причина: схема не разделяет `nightHours` на
«ночные обычные» и «ночные сверхурочные» — данных для корректного
начисления ночной надбавки поверх OT-множителя просто нет. См. D2 в
разделе 5.

### 2.4 holidayAmount

```
rowHoliday = T.isHoliday
  ? (T.regularHours + T.overtimeHours) × rate × (R.holidayPct / 100)
  : 0
```

В праздничную надбавку входят **все** отработанные в этот день часы
(обычные + сверхурочные), потому что `isHoliday` — признак всей смены, а
не отдельных часов. Процент применяется к базовой ставке (не к сумме,
уже увеличенной OT-множителем) — надбавки не компаундируются друг с
другом. См. D3 в разделе 5 — компаундирование vs аддитивность само по
себе региональный вопрос, не только величина процента.

### 2.5 remoteBonusAmount

```
rowRemote = (rowBase + rowOvertime) × (R.remoteBonusPct / 100)
```

База начисления — уже заработанные `baseAmount + overtimeAmount` за эту
строку (т.е. вахтовая/удалённая надбавка учитывает и переработку). См.
D4 в разделе 5 — альтернатива «только от regularHours» тоже
рассматривалась и отклонена, но требует подтверждения.

### 2.6 perDiemAmount (суточные)

Считается **не по строкам табеля, а по уникальным календарным дням**,
чтобы не задвоить суточные, если на одну дату есть несколько строк
табеля (например, раздельные смены/правки):

```
для каждой уникальной пары (employeeId, workDate) среди locked-табелей периода:
    R_date = победившее правило (по алгоритму раздела 1) для табеля(-ей) этой даты
    perDiem(date) = R_date.perDiemAmount

perDiemAmount(period) = Σ perDiem(date) по всем уникальным датам
```

Если в один день у сотрудника есть табели на **разных** участках
(редкий, но не запрещённый схемой случай) — это не покрыто данной
спецификацией, см. открытый вопрос D7 в разделе 5.

### 2.7 pieceRateAmount (сдельная премия за метраж)

```
rowPieceRate = (T.metersDrilled ?? 0) × R.perMeterBonus
pieceRateAmount(period) = Σ rowPieceRate по всем строкам табеля периода
```

### 2.8 deductions — вне скоупа формулы

Удержание налога (НДФЛ и т.п.) **не вычисляется автоматически** — ни один
процент не зафиксирован ни в плане, ни в схеме. Значение по умолчанию —
`0`, либо ручной ввод бухгалтером через `deductionsByEmployee` на входе
расчёта. **Это отдельный открытый вопрос**, который не входит в раздел
10 п.1 плана (там речь только про вахту/переработки/суточные) — см.
D8, рекомендация добавить его в план явно.

### 2.9 advanceDeduction — внешний вход, не формула

`advanceDeduction` **не читается из БД** (в схеме нет модели «Аванс») —
это ручной ввод бухгалтера в момент запуска расчёта, по
`employeeId → сумма`. Спецификация фиксирует контракт входа:

```
advanceDeductionByEmployee: Map<employeeId, Decimal>
```

Если для сотрудника в карте нет значения — `advanceDeduction = 0`.
См. D9 в разделе 5 — риск отсутствия аудиторского следа для авансов.

### 2.10 netAmount

```
netAmount = baseAmount + overtimeAmount + nightAmount + holidayAmount
          + remoteBonusAmount + perDiemAmount + pieceRateAmount
          - deductions - advanceDeduction
```

## 3. Округление

- Всё промежуточное сложение (по строкам табеля за период) выполняется
  **без округления**, в полной десятичной точности (`Decimal`,
  библиотека с фиксированной точностью, не `Number`/`float`).
- Округление до 2 знаков (копейки) выполняется **один раз**, в момент
  формирования каждого поля `PayrollLine` (`baseAmount`,
  `overtimeAmount`, ..., `netAmount`) — не на промежуточных шагах и не
  по каждой строке табеля отдельно. Это исключает накопление ошибки
  округления при суммировании множества строк.
- Способ округления — **арифметическое (round half up / «от нуля»)**,
  не банковское (round half to even). Это низкорисковое допущение
  (легко меняется одной функцией), но фиксирую как D10 в разделе 5 на
  случай, если учётная политика компании требует иного.
- `netAmount` пересчитывается из уже округлённых компонентов (сумма
  округлённых чисел, минус округлённые `deductions`/`advanceDeduction`),
  после чего округляется ещё раз защитным шагом (в норме уже точное
  число).

## 4. Расчётный лист — требование объяснимости

`PayrollLine` обязан содержать (уже есть в схеме) отдельно все суммы
раздела 2. Бухгалтер должен быть способен вручную проверить `netAmount`
по формуле раздела 2.10, имея под рукой: список locked-табелей
сотрудника за период, применённую для каждой строки `RateRule` (её
`name` и `id` — **рекомендация**: расчёт должен сохранять/логировать,
какое правило было применено к какой строке табеля, иначе повторную
проверку бухгалтером выполнить нельзя — это прямое требование раздела 4
плана «расчёт объясним, а не чёрный ящик»). Считаю это обязательным, а
не опциональным логом.

## 5. Решения, принятые самостоятельно — требуют подтверждения

Ничего из региональных норм (сами проценты/суммы) я не придумываю — их
вводит владелец через `RateRule`. Ниже — решения о **механике применения**
уже введённых значений, которые не были явно описаны ни в плане, ни в
схеме, и которые я принял сам, чтобы формула вообще была детерминированной.

- **D1 (важное).** Победитель `RateRule` выбирается **целиком** (все
  поля из одной строки), а не пофилево. Риск: узкоспециализированное, но
  высокоприоритетное правило может «обнулить» надбавки из более общего
  правила, даже если оно их не затрагивает по смыслу (см. сценарий F —
  разница в примере ≈ 2000 ₽ на одном табеле). Альтернатива —
  пофилевое наследование — потребует ADR + миграции схемы (nullable
  поля в `RateRule`, чтобы отличать «не задано» от «явно 0»). Решение
  нужно от архитектора/владельца: принять риск текущей схемы или
  запросить миграцию.
- **D2.** Ночная надбавка считается от базовой ставки, не поверх
  сверхурочного множителя (нет поля, разделяющего `nightHours` на
  обычные/сверхурочные). Если региональная норма требует иного —
  нужно новое поле в `Timesheet` (например `nightOvertimeHours`).
- **D3.** Праздничная надбавка — на все часы дня (regular+overtime),
  процент от базовой ставки, без компаундирования с OT-множителем.
  Компаундирование — тоже региональный вопрос, не только величина
  процента; предлагаю явно добавить эту развилку в раздел 10 плана
  рядом с пунктом 1.
- **D4.** Вахтовая/удалённая надбавка (`remoteBonusPct`) считается от
  `baseAmount + overtimeAmount` строки, не только от `regularHours`.
  Также отмечаю смысловое пересечение `remoteBonusPct` и
  `perDiemAmount` — оба поля описывают вахтовую компенсацию. Стоит
  уточнить у владельца, чем они отличаются по замыслу (одна — процент
  от заработка, другая — фиксированная сумма в день), чтобы не задвоить
  компенсацию за один и тот же факт.
- **D5.** Тай-брейк при равном `priority` — специфичность
  (участок+должность > один из двух > ни один), затем `createdAt`.
  Разумный дефолт, не описан явно нигде — прошу подтвердить.
- **D6.** Правило выбирается **по каждой строке табеля отдельно** (по
  `Timesheet.siteId`), а не один раз на сотрудника за период — из-за
  возможности работы на разных участках в одном периоде.
- **D7.** Суточные (`perDiemAmount`) дедуплицируются по уникальной дате
  (`employeeId + workDate`), не по строке табеля — иначе задваиваются
  при нескольких табелях на одну дату. Случай «два разных участка в
  один день у одного сотрудника» не покрыт — предлагаю это либо
  запретить на уровне бизнес-правила (валидация табеля), либо явно
  прописать, суточные какого участка считать приоритетными.
- **D8.** Удержание налога — не формула, вход `0` или ручной ввод.
  Это отдельный открытый вопрос, не входящий в раздел 10 п.1 плана
  (там только вахта/переработки/суточные) — предлагаю дополнить план.
- **D9.** `advanceDeduction` — внешний вход без хранения в БД (нет
  модели «Аванс»). Риск: нет аудиторского следа выданных авансов между
  расчётами. Рекомендую backend-dev/архитектору рассмотреть
  персистентную модель `Advance`/`Deduction`, привязанную к
  `Employee` — это уже не моя зона (формула), а зона данных.
- **D10.** Округление — арифметическое (не банковское), один раз на
  финальных суммах компонента, не на промежуточных шагах. Низкий риск,
  но фиксирую явно.
- **D11.** Отсутствие подходящего `RateRule` для строки табеля — ошибка
  валидации, блокирующая расчёт, а не тихий нулевой результат.
  Рекомендация backend-dev: обеспечить инвариант «у каждой компании
  всегда есть минимум один wildcard `RateRule`» (например, создавать
  автоматически при создании компании с нулевыми значениями).

## 6. Тестовые сценарии (контракт backend-dev / qa-tester)

Общие данные, если не указано иное: `Company` без иных активных правил,
кроме перечисленных в сценарии. Ставки/проценты — иллюстративные, не
нормы закона.

### Сценарий А — простая смена без надбавок

- Должность: `baseHourlyRate = 500`, `overtimeMultiplier = 1.5`.
  Сотрудник без `baseRateOverride`.
- Правило: только wildcard `RateRule` компании, все проценты/суммы = 0.
- Табель: `regularHours=8, overtimeHours=0, nightHours=0, isHoliday=false, metersDrilled=null`.

| Поле | Расчёт | Сумма |
|---|---|---|
| baseAmount | 8 × 500 | **4000** |
| overtimeAmount | — | 0 |
| nightAmount | — | 0 |
| holidayAmount | — | 0 |
| remoteBonusAmount | — | 0 |
| perDiemAmount | — | 0 |
| pieceRateAmount | — | 0 |
| deductions | вход | 0 |
| advanceDeduction | вход | 0 |
| **netAmount** | | **4000** |

### Сценарий Б — смена со сверхурочными

- Ставка 500 ₽/ч, `overtimeMultiplier = 1.5`.
- Табель: `regularHours=8, overtimeHours=2` (10-часовая смена, из них 2 сверхурочных).

| Поле | Расчёт | Сумма |
|---|---|---|
| baseAmount | 8 × 500 | 4000 |
| overtimeAmount | 2 × 500 × 1.5 | 1500 |
| **netAmount** | 4000 + 1500 | **5500** |

### Сценарий В — ночная смена

- Ставка 500 ₽/ч. `RateRule` (wildcard по компании): `nightShiftPct = 20`.
- Табель: `regularHours=8, overtimeHours=0, nightHours=4` (4 из 8 часов — ночные).

| Поле | Расчёт | Сумма |
|---|---|---|
| baseAmount | 8 × 500 | 4000 |
| nightAmount | 4 × 500 × 0.20 | 400 |
| **netAmount** | 4000 + 400 | **4400** |

### Сценарий Г — праздничная смена (с переработкой)

- Ставка 500 ₽/ч, `overtimeMultiplier = 1.5`. `RateRule`: `holidayPct = 100`.
- Табель: `regularHours=8, overtimeHours=2, isHoliday=true, nightHours=0`.

| Поле | Расчёт | Сумма |
|---|---|---|
| baseAmount | 8 × 500 | 4000 |
| overtimeAmount | 2 × 500 × 1.5 | 1500 |
| holidayAmount | (8+2) × 500 × 1.00 | 5000 |
| **netAmount** | 4000+1500+5000 | **10500** |

### Сценарий Д — сдельная премия за метраж

- Ставка 500 ₽/ч. `RateRule`: `perMeterBonus = 150`.
- Табель: `regularHours=8, overtimeHours=0, metersDrilled=12.5`.

| Поле | Расчёт | Сумма |
|---|---|---|
| baseAmount | 8 × 500 | 4000 |
| pieceRateAmount | 12.5 × 150 | 1875 |
| **netAmount** | 4000+1875 | **5875** |

### Сценарий Е — пересечение нескольких RateRule разного приоритета

Сотрудник «Иванов», должность «Бурильщик»: `baseHourlyRate=600`,
`overtimeMultiplier=1.5`. Участок `SITE_A`.

Правила компании:

| Правило | siteId | positionId | priority | nightShiftPct | holidayPct | remoteBonusPct | perDiemAmount | perMeterBonus |
|---|---|---|---|---|---|---|---|---|
| R1 (компания) | null | null | 0 | 10 | 50 | 0 | 500 | 0 |
| R2 (участок SITE_A) | SITE_A | null | 5 | 0 | 0 | 20 | 800 | 0 |
| R3 (должность) | null | Бурильщик | **10** | 25 | 0 | 0 | 0 | 120 |

Табель: `siteId=SITE_A, regularHours=8, overtimeHours=1, nightHours=3, isHoliday=false, metersDrilled=10`.

Все три правила — кандидаты (siteId и/или positionId совпадают или
null). По `priority` побеждает **R3** (priority=10 — выше остальных),
несмотря на то что R2 более специфичен по участку. Используются **только**
поля R3 целиком: `nightShiftPct=25, holidayPct=0, remoteBonusPct=0,
perDiemAmount=0, perMeterBonus=120`.

| Поле | Расчёт | Сумма |
|---|---|---|
| baseAmount | 8 × 600 | 4800 |
| overtimeAmount | 1 × 600 × 1.5 | 900 |
| nightAmount | 3 × 600 × 0.25 (из R3) | 450 |
| holidayAmount | isHoliday=false | 0 |
| remoteBonusAmount | R3.remoteBonusPct=0 → **не** 20% из R2 | 0 |
| perDiemAmount | R3.perDiemAmount=0 → **не** 800 из R2 | 0 |
| pieceRateAmount | 10 × 120 (из R3) | 1200 |
| **netAmount** | 4800+900+450+1200 | **7350** |

Если бы вместо «победитель целиком» применялось пофилевое наследование
(альтернатива из D1: `remoteBonusPct` и `perDiemAmount` брались бы из
R2, раз R3 их не переопределяет), результат был бы:
`remoteBonusAmount = (4800+900) × 0.20 = 1140`, `perDiemAmount = 800`,
**netAmount = 9290** — на 1940 ₽ больше. Разница наглядно показывает,
почему D1 нужно подтвердить явно, а не решать по умолчанию.
