# 0004 — Движок расчёта зарплаты: решения по спецификации payroll-rules

- Статус: принято
- Дата: 2026-09-05
- Автор: architect (по спецификации агента `payroll-rules`,
  `docs/payroll-formulas.md`)

## Контекст

Перед реализацией Этапа 03 агент `payroll-rules` формализовал точную
формулу расчёта (`docs/payroll-formulas.md`) и явно выделил 11 решений
(D1–D11), которые пришлось принять самостоятельно, потому что они не
описаны ни в `docs/project-plan.md`, ни однозначно не следуют из схемы
Prisma. Ниже — решения по каждому пункту, принятые архитектором, чтобы
не блокировать реализацию.

## Решения

- **D1 (главное).** Принимаю риск текущей схемы: при пересечении
  `RateRule` побеждает **одно правило целиком** (по `priority`, затем
  специфичности, затем `createdAt`), а не пофилевое наследование.
  Причина принятия, а не миграции: пофилевое наследование потребовало бы
  делать все Decimal-поля `RateRule` nullable (различать «не задано» и
  «явно 0»), это ломающая миграция ради формулировки из плана, которая
  на момент написания ещё не проверена реальным сценарием использования.
  **Если/когда владелец компании столкнётся с необходимостью точечного
  переопределения одной надбавки** (см. пример в спецификации, разница
  ≈2000 ₽) — заводим отдельный ADR и миграцию тогда, не заранее.
- **D2.** Принимаю: ночная надбавка — от базовой ставки, не поверх OT.
  Если региональная норма потребует иначе — добавить
  `Timesheet.nightOvertimeHours` отдельным полем, не переиспользовать
  `nightHours`.
- **D3.** Принимаю: праздничная надбавка на все часы смены
  (regular+overtime), без компаундирования с OT-множителем.
- **D4.** Принимаю: `remoteBonusPct` — от `baseAmount + overtimeAmount`
  строки. Отдельно фиксирую предупреждение payroll-rules о смысловом
  пересечении `remoteBonusPct` и `perDiemAmount` — **открытый вопрос
  пользователю**, добавлен в `docs/project-plan.md`, раздел 10, наравне
  с региональными нормами: чем именно должны отличаться вахтовая
  надбавка (% от заработка) и суточные (фиксированная сумма/день) в
  реальной практике компании.
- **D5.** Принимаю тай-брейк: специфичность → `createdAt`.
- **D6.** Принимаю: правило выбирается на каждую строку табеля
  отдельно (по `Timesheet.siteId`), не один раз на сотрудника за период.
- **D7.** Принимаю дедупликацию суточных по `(employeeId, workDate)`.
  Случай «два участка в один день» **не валидируется** на уровне API в
  этой версии — при коллизии берётся участок первой по порядку выборки
  строки табеля. Если это станет реальной проблемой — валидация на
  уровне `TimesheetsService.create` (запрет второй записи на ту же дату
  с другим `siteId`), не в движке расчёта.
- **D8.** Принимаю: удержание налога — вне формулы, ручной вход
  (`deductions` в `RunPayrollDto`, по умолчанию 0). Добавлено в раздел
  10 плана как отдельный открытый вопрос.
- **D9.** Принимаю риск отсутствия персистентного аудита авансов в этой
  версии: `advanceDeduction` — ручной ввод при каждом запуске расчёта
  (`RunPayrollDto.advances`), не читается из БД. **Бэклог**: модель
  `Advance` (кто, когда, сколько выдано наличными между расчётами) —
  Этап 03+, не блокирует текущий релиз, но нужна до реального
  использования в проде (иначе бухгалтер обязан помнить выданные авансы
  между запусками сам).
- **D10.** Принимаю арифметическое округление (не банковское), один раз
  на финальных суммах компонентов.
- **D11.** Принимаю: отсутствие подходящего `RateRule` — ошибка
  валидации (`BadRequestException`), откатывающая весь запуск расчёта
  через транзакцию (`PayrollService.runPayroll` теперь оборачивает
  создание `PayrollRun`/`PayrollLine` в `prisma.$transaction`). Инвариант
  «у компании всегда есть хотя бы один wildcard `RateRule`»
  обеспечивается в `prisma/seed.ts` для демо-компании; для реального
  онбординга новой компании (когда появится такой сценарий) это должно
  создаваться автоматически при создании компании — зафиксировано как
  TODO для `backend-dev`.

## Объяснимость расчёта

Требование плана «расчёт объясним, а не чёрный ящик» закрыто частично:
`PayrollCalcService.calculateForEmployee` возвращает `appliedRules` —
список (табель → применённое правило) в ответе API при запуске расчёта.
Это **не персистится** в БД (схема `PayrollLine` не хранит связь с
конкретным `RateRule` построчно) — значит, эту разбивку можно увидеть
только в момент запуска расчёта, а не при просмотре истории
(`GET /payroll/runs/:id`) позже. Если для аудита понадобится
восстанавливать её ретроспективно — нужна отдельная таблица
`PayrollLineRuleApplication` (табель → правило → сумма), это Этап 03+
бэклог, не блокирует текущий релиз.

## Последствия

- `docs/project-plan.md`, раздел 10, дополнен пунктами о налоговых
  удержаниях и разграничении `remoteBonusPct`/`perDiemAmount` — оба
  требуют ответа пользователя до того, как реальные компании смогут
  положиться на цифры расчёта.
- Любое изменение формулы должно синхронно обновлять и
  `docs/payroll-formulas.md`, и этот ADR, и тестовые сценарии
  `qa-tester`'а — иначе спецификация и код разойдутся молча.
