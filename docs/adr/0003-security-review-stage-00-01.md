# 0003 — Ревью безопасности Этапов 00–01 и устранение находок

- Статус: принято
- Дата: 2026-09-05
- Автор: security-reviewer (ревью), backend/frontend-dev (фиксы)

## Контекст

После завершения Этапа 01 запущено ревью безопасности агентом
`security-reviewer` по всему коду `apps/api/src`. Поводом послужила
реальная находка при живой проверке: `GET /crews` отдавал бригадира
через `include: { foreman: true }`, что тянуло `passwordHash` прямо в
HTTP-ответ (закрыто ещё до ревью, см. коммит Этапа 01).

Ревью нашло три критичных проблемы, три высокого приоритета и несколько
среднего — полный список см. в отчёте агента (не хранится в репозитории
как файл, только как решения ниже).

## Решение — исправлено немедленно

1. **Эскалация привилегий через `POST /users`.** Раньше единственная
   проверка `roleId` — что роль принадлежит компании. Любой с правом
   `user:create` (HR по сиду) мог узнать id роли «Владелец» через
   `GET /roles` и выдать её кому угодно. Исправлено: `UsersService`
   теперь сравнивает полный набор прав целевой роли с эффективными
   правами вызывающего — выдать роль шире собственной нельзя.
2. **IDOR в табелях.** `TimesheetsService.create`/`transition` проверяли
   только факт права `(timesheet, action)`, не привязку к конкретной
   записи — бригадир мог отправить табель за чужую бригаду, руководитель
   участка мог согласовать/заблокировать табель чужого участка, зная
   его id. Также `findAll` использовал захардкоженный `ownCrewIds = []`
   (TODO с Этапа 00), из-за чего `own_crew`-scope на чтение был
   fail-closed и ветка кода фактически не тестировалась. Исправлено:
   добавлен `assertInScope()`, сверяющий реальные `crewId`/`siteId`
   записи со scope пользователя; `ownCrewIds` считается по факту
   `Crew.foremanId === user.id`.
3. **Fallback JWT-секрет в исходниках.** `jwt.strategy.ts`/`auth.module.ts`
   тихо подписывали токены строкой `'change-me-before-any-real-deployment'`
   при отсутствии `JWT_SECRET`. Хуже того — выяснилось, что приложение
   **вообще нигде не загружало `.env`** (только Prisma CLI грузит его
   для миграций), то есть весь этот путь мог срабатывать на пустом
   месте. Исправлено: `src/config/jwt-secret.ts` — явный отказ от
   старта при отсутствии секрета или использовании значения-заглушки;
   `main.ts` теперь первым импортом грузит `dotenv/config` до импорта
   `AppModule` (важно: именно до, потому что `JwtModule.register()`
   читает `process.env` в момент импорта модуля, а не внутри `bootstrap()`).
4. **Токен не отзывался при деактивации.** `JwtStrategy.validate()`
   доверял payload'у до истечения TTL (до 8ч) даже для уволенного
   бригадира — прямое нарушение раздела 6 плана про офлайн-токены.
   Исправлено: `validate()` теперь подгружает пользователя из БД и
   проверяет `isActive` на каждый запрос.
5. **Нет защиты от брутфорса логина.** Добавлен `@nestjs/throttler`:
   5 попыток в минуту на `/auth/login`.
6. **`PayrollService.runPayroll` игнорировал scope.** По сиду сейчас не
   эксплуатируется (только `company`-scope роли имеют `payroll:create`),
   но модель прав прямо допускает кастомную роль с `own_sites` — добавлена
   фильтрация сотрудников по scope вызывающего.
7. **Общая офлайн-очередь табелей на устройстве.** `localStorage`-ключ
   был один на всё устройство — при передаче планшета между бригадирами
   в поле следующий вошедший видел бы чужие несинхронизированные
   записи. Исправлено: очередь ключуется по `userId` (`lib/session.ts` +
   обновлённый `lib/offlineQueue.ts`); синхронизированные записи сразу
   удаляются, а не копятся.
8. **`foremanId` не проверялся на принадлежность компании.** Не
   эксплуатируется при одной компании в БД, но зафиксировано на будущее
   (мультитенантность — открытый вопрос плана, раздел 10): добавлена
   проверка `companyId` перед назначением бригадира.
9. **CORS был открыт для любого origin.** Сужен до `WEB_ORIGIN`
   (по умолчанию `http://localhost:5173`).

## Отложено в бэклог (не блокирует Этап 02)

- `npm audit`: 21 находка, ни одной critical. `multer` (транзитивно
  через `@nestjs/platform-express`) сейчас нигде не используется, но
  **обязательно проверить перед добавлением загрузки фото к табелю**
  (Этап 02, поле `Timesheet.photoUrls` уже в схеме).
- Мажорный апгрейд `@nestjs/*` и `vite` — отдельной задачей с
  регрессионным тестированием, не point-фиксом.
- JWT в `localStorage` на фронтенде — известный компромисс (уязвим к
  XSS-эксфильтрации), сознательно принят, не критично при текущем
  масштабе.

## Последствия

- Любой новый write-эндпоинт, работающий с конкретной записью (не
  списком), обязан явно проверять принадлежность записи scope
  вызывающего — простого `@RequirePermission` на уровне (ресурс,
  действие) недостаточно, это подтверждено дважды в этом ревью
  (табели, а до этого — бригады на Этапе 01).
- `security-reviewer` включается в процесс перед каждым мерджем,
  трогающим RBAC/auth/scope-фильтрацию, а не только по итогам этапа.
