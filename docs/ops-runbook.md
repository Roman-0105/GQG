# КЕРН — инструкция по эксплуатации (пилот)

Эта инструкция — для человека, который отвечает за то, чтобы платформа
работала на компьютере/сервере компании во время пилота (Этап 06
дорожной карты, `docs/project-plan.md`, раздел 9). Программистом быть
не нужно — все команды даны как есть, копируются и вставляются в
терминал.

## Что нужно установить

Один раз, на компьютере/сервере, где будет крутиться КЕРН:

1. **Docker Desktop** (Windows/macOS) или **Docker Engine + Compose
   plugin** (Linux-сервер) — https://www.docker.com/products/docker-desktop/
   После установки Docker Desktop должен быть запущен (иконка кита в
   трее) — без него ничего из инструкции ниже не сработает.
2. Сам код платформы — папка репозитория КЕРН на этом компьютере
   (например, `D:\Projects\GQS`, см. `README.md` про требования к пути
   на Windows).

Node.js/PostgreSQL ставить на сам хост **не нужно** — они живут внутри
Docker-контейнеров.

## Первый запуск

Все команды — из корня репозитория (папка, где лежит файл
`docker-compose.yml`).

### 1. Настроить секреты

```bash
cp .env.example .env
```

Откройте `.env` в блокноте и замените два плейсхолдера:

- `POSTGRES_PASSWORD` — придумайте пароль или сгенерируйте:
  `openssl rand -hex 16` (Git Bash/WSL) — или просто наберите любой
  длинный случайный набор символов руками.
- `JWT_SECRET` — обязательно сгенерируйте случайное значение:
  `openssl rand -hex 32`. **Не оставляйте плейсхолдер** — сервер
  откажется запускаться со значением-заглушкой (это специально, см.
  `apps/api/src/config/jwt-secret.ts`).

Остальные значения (`WEB_ORIGIN`, `VITE_API_URL`, порты) по умолчанию
рассчитаны на то, что всё открывается с того же компьютера
(`http://localhost:8080`). Если бригадиры будут заходить с планшетов по
Wi-Fi на этот же сервер — см. врезку ниже.

> **Доступ с планшетов/телефонов в поле по Wi-Fi.** `localhost` работает
> только на самом сервере. Чтобы панель открывалась с других устройств
> в той же сети, узнайте LAN-IP сервера (`ipconfig` → `IPv4 Address`,
> например `192.168.1.50`) и замените в `.env`:
> ```
> WEB_ORIGIN=http://192.168.1.50:8080
> VITE_API_URL=http://192.168.1.50:3000
> ```
> Это нужно сделать **до** первого `docker compose up --build`
> (см. предупреждение про `VITE_API_URL` в `apps/web/Dockerfile`) —
> если поменяли уже после сборки, пересоберите web:
> `docker compose build web && docker compose up -d web`.

### 2. Поднять всё окружение

```bash
docker compose up -d --build
```

Первый раз это займёт несколько минут (Docker скачивает образы
PostgreSQL/nginx и собирает backend/веб-панель). При старте backend сам
применит все накопленные миграции базы данных — руками ничего создавать
не нужно.

### 3. Проверить, что всё работает

```bash
docker compose ps
```

Все три сервиса (`postgres`, `api`, `web`) должны быть в статусе `Up`
(со временем — `healthy`). Откройте в браузере `http://localhost:8080`
(или `http://<LAN-IP>:8080` для доступа по сети) — должна открыться
страница входа КЕРН.

### 4. Завести реальную компанию и владельца

**Важная особенность на сегодняшний день (см. находку ниже):** в
продукте пока нет формы регистрации новой компании и нет способа
сменить пароль через интерфейс. Единственный встроенный способ создать
первого пользователя — сид-скрипт, который создаёт демо-компанию и
владельца `owner@demo.kern` / `change-me-now`.

Для пилота с реальными людьми это нужно сделать так:

```bash
docker compose exec api npx prisma db seed --schema=./prisma/schema.prisma
```

Дальше:
1. Зайдите в панель под `owner@demo.kern` / `change-me-now`.
2. Переименуйте демо-компанию и заведите реальных пользователей/роли
   через раздел «Пользователи» — там уже можно создавать логины с
   собственным паролем для остальных сотрудников (это работает).
3. **Пароль самого `owner@demo.kern` сменить через интерфейс нельзя —
   такого эндпоинта в API пока нет** (см. находку ниже). Временный
   обходной путь: создайте себе второго пользователя с ролью
   «Владелец компании» и полноценным паролем через раздел
   «Пользователи», проверьте, что вход под ним работает, и деактивируйте
   (`isActive = false`) `owner@demo.kern` тем же способом. Деактивация
   отзывает доступ немедленно (см. `JwtStrategy.validate`).

> **Находка для эскалации (не устраняется этой инструкцией):** в API
> нет ни формы саморегистрации компании, ни эндпоинта смены/сброса
> пароля (`UpdateUserDto` не содержит поля пароля). Перед реальным
> пилотом с деньгами это стоит закрыть на уровне backend — иначе
> единственный официальный путь входа в свежую систему держится на
> захардкоженном демо-пароле. Это зона `backend-dev`/`architect`, не
> devops — здесь только описан текущий обходной путь.

## Повседневная работа: запуск, остановка, логи

Всё — из корня репозитория.

| Действие | Команда |
|---|---|
| Запустить (если уже собрано) | `docker compose up -d` |
| Остановить всё | `docker compose down` |
| Остановить, но оставить данные БД | `docker compose down` (том с данными БД не удаляется — см. ниже) |
| Остановить и **удалить данные БД** (осторожно!) | `docker compose down -v` |
| Перезапустить один сервис | `docker compose restart api` |
| Посмотреть статус | `docker compose ps` |
| Посмотреть логи backend | `docker compose logs -f api` |
| Посмотреть логи БД | `docker compose logs -f postgres` |
| Посмотреть логи веб-панели | `docker compose logs -f web` |
| Посмотреть логи всех сразу | `docker compose logs -f` |

`docker compose down` **не удаляет** данные PostgreSQL — они лежат в
именованном Docker-томе `kern_postgres_data` и переживают остановку и
пересоздание контейнеров. Удаляет данные только явный флаг `-v`.

## Резервное копирование

### Вручную, в любой момент

```bash
node tools/ops/backup.js
```

Создаст файл `backups/kern-<дата-время>.dump` в корне репозитория и
автоматически удалит бэкапы старше последних 14 (настраивается
переменной окружения `KERN_BACKUP_KEEP`). Папка `backups/` не попадает
в git (это реальные данные компании).

### Автоматически по расписанию (Windows, Планировщик заданий)

1. Откройте «Планировщик заданий» (Task Scheduler).
2. «Создать простую задачу» → назвать, например, `КЕРН — бэкап БД`.
3. Триггер: «Ежедневно», время — вне рабочей смены (например, 03:00).
4. Действие: «Запустить программу».
   - Программа/сценарий: `powershell.exe`
   - Аргументы: `-NoProfile -ExecutionPolicy Bypass -File "D:\Projects\GQS\tools\ops\backup.ps1"`
     (путь замените на реальный путь к репозиторию на этом компьютере)
   - Рабочая папка: `D:\Projects\GQS`
5. Сохранить. Задачу можно запустить вручную кнопкой «Выполнить», чтобы
   сразу проверить, что бэкап создаётся (`backups/` пополнился новым
   файлом).

На Linux-сервере (если платформа переедет на VPS — см. открытые
вопросы) — та же логика через cron и `tools/ops/backup.sh`, пример
строки cron есть в комментарии в самом файле.

### Проверка бэкапов (обязательно, не реже раза в 2-3 недели пилота)

Бэкап, который никто не пробовал развернуть, — не бэкап. Периодически
проверяйте восстановление на тестовой копии, а не на боевой БД:

```bash
# Поднять отдельную временную БД для проверки (порт 5433, чтобы не
# конфликтовать с боевой на 5432):
docker run --rm -d --name kern-restore-test -e POSTGRES_PASSWORD=test -p 5433:5432 postgres:16-alpine

# Восстановить в неё последний бэкап (замените имя файла на актуальное):
docker exec -i kern-restore-test pg_restore -U postgres -d postgres --create --clean --if-exists < backups/kern-20260906T030000.dump

# Заглянуть, что данные реально есть (например, список компаний):
docker exec -it kern-restore-test psql -U postgres -d kern -c "select count(*) from \"Company\";"

# Убрать тестовый контейнер:
docker rm -f kern-restore-test
```

Если эта проверка когда-нибудь не пройдёт — это сигнал разбираться
немедленно, а не откладывать до реального сбоя.

## Восстановление после сбоя

### Сценарий: нужно вернуть БД из бэкапа (авария, ошибка, потеря данных)

**Прежде всего остановите backend** — иначе он продолжит писать в базу
поверх процесса восстановления:

```bash
docker compose stop api
```

Затем:

```bash
node tools/ops/restore.js backups/kern-20260906T030000.dump --yes
```

(замените имя файла на нужный бэкап; список файлов — `dir backups` /
`ls backups`). Скрипт сам откажется работать, если забыли `--yes`, и
сам проверит, что `api` действительно остановлен.

После восстановления:

```bash
docker compose start api
```

Зайдите в панель и убедитесь, что данные на месте, прежде чем
возвращать людей к работе.

### Сценарий: после перезагрузки сервера контейнеры не поднялись сами

Все сервисы в `docker-compose.yml` запускаются с политикой
`restart: unless-stopped` — Docker должен сам поднять их заново после
перезагрузки хоста или падения Docker-демона, **если только их не
останавливали руками командой `docker compose down`/`stop` перед этим**
(в этом случае `unless-stopped` как раз уважает то, что их остановили
намеренно, и не поднимет автоматически).

Если после перезагрузки сервера панель недоступна:

1. Проверьте, что Docker Desktop вообще запущен (на Windows он должен
   стартовать вместе с системой — если это не так, включите автозапуск
   в настройках Docker Desktop → Settings → General → «Start Docker
   Desktop when you log in»).
2. `docker compose ps` — если сервисов вообще нет в списке, значит
   Docker поднялся уже после того, как кто-то выполнил `docker compose
   down`. Поднимите руками: `docker compose up -d`.
3. Если сервисы есть, но не `healthy` — смотрите логи (`docker compose
   logs -f api`) на предмет ошибки подключения к БД или неверного
   `.env`.

### Сценарий: сервер компании недоступен физически (не включается, сеть легла)

Пока сервер не восстановлен, полевые бригадиры **не теряют данные**:
табель на планшете/телефоне пишется сначала в локальную очередь на
самом устройстве (см. `docs/project-plan.md`, раздел 6, и
`apps/web/src/lib/offlineQueue.ts`) и ждёт связи с сервером, чтобы
отправиться. Это уже реализовано на уровне веб-приложения независимо
от того, поднят сервер или нет — восстанавливать здесь на стороне
инфраструктуры нечего, кроме самого сервера.

Что делать:
1. Как можно быстрее вернуть сервер в строй (или поднять окружение на
   резервной машине из последнего бэкапа — те же шаги «Первый запуск» +
   «Восстановление БД из бэкапа» выше).
2. Бригадиры продолжают заполнять табели офлайн — как только сервер
   снова доступен по тому же адресу (`VITE_API_URL`), очередь
   синхронизируется сама при следующем открытии приложения с сетью.
3. Если сервер поднимается на новом адресе/IP (например, временно на
   другом компьютере) — веб-панель нужно пересобрать с новым
   `VITE_API_URL` (см. «Первый запуск»), иначе браузеры продолжат
   стучаться по старому адресу.

## Типичные проблемы

**«Порт уже занят» при `docker compose up`.**
Скорее всего на компьютере уже что-то слушает 5432/3000/8080 (например,
локально установленный PostgreSQL для разработки). Поменяйте порт в
`.env` (`POSTGRES_PORT`, `API_PORT`, `WEB_PORT`) на свободный и
перезапустите `docker compose up -d`.

**Панель открывается, но при входе пишет «Нет соединения с сервером».**
Проверьте `VITE_API_URL` в `.env` — браузер должен достучаться именно
до этого адреса. Если недавно меняли адрес сервера — не забыли ли
пересобрать `web` (`docker compose build web`)? См. врезку в разделе
«Первый запуск».

**`docker compose up` пишет что-то про `JWT_SECRET`/`POSTGRES_PASSWORD` и требует их заполнить.**
Это специальная защита — сервер намеренно не запускается с пустыми
секретами. Откройте `.env`, заполните оба значения (см. «Первый
запуск», шаг 1).

**Диск заполняется бэкапами/логами Docker.**
Бэкапы ротируются автоматически (последние 14 хранятся), но старые
образы Docker после многократных пересборок (`docker compose build`)
могут копиться отдельно. Периодически: `docker image prune -f`.

## Открытые вопросы, которые нужно решить отдельно

Эти решения — не техническая деталь инфраструктуры, их принимает
владелец компании/архитектор, не devops (см. `docs/project-plan.md`,
раздел 10):

- **Локальный сервер компании или VPS?** От этого зависит, нужен ли
  проброс портов наружу, статический IP/домен, и стоит ли переносить
  `backup.sh`/cron вместо `backup.ps1`/Task Scheduler. Конфигурация
  выше рассчитана на локальный сервер в локальной сети; для VPS
  дополнительно потребуется отдельно продумать сетевой доступ и,
  скорее всего, HTTPS (сейчас всё поднимается по обычному HTTP — не
  проблема в закрытой локальной сети, но проблема, если панель
  смотрит наружу в интернет).
- **Отсутствие формы регистрации и смены пароля** (см. раздел «Первый
  запуск», находка выше) — эскалировано архитектору/backend-dev,
  требует решения на уровне продукта, не инфраструктуры.
