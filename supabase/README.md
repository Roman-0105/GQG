# Supabase — схема БД и применение миграций

## Как применить миграции

Файлы в `migrations/` применять **по порядку номеров**, целиком, в
Supabase Dashboard → **SQL Editor** → New query → вставить содержимое
файла → **Run**:

1. `0001_init_schema.sql` — таблицы
2. `0002_rls_policies.sql` — RLS-политики (обязательно после 0001)
3. `0003_seed_reference_data.sql` — стартовые справочники (необязательно, но полезно)

Если у вас настроен Supabase CLI локально — то же самое можно сделать
через `supabase db push`, но пока делаем через SQL Editor, это проще
без лишней настройки CLI.

## Важно: первый пользователь (bootstrap)

RLS-политика на `profiles` разрешает **создавать** профили только тем,
у кого уже есть роль `general_director`/`technical_director`
(`is_management()`). Но самого первого пользователя таким образом
создать нельзя — некому его одобрить. Поэтому первый раз — вручную:

1. Зарегистрируйте пользователя обычным способом: либо через форму входа
   на сайте (когда она появится), либо в Supabase Dashboard →
   **Authentication → Users → Add user** (укажите email/пароль)
2. Скопируйте `UID` созданного пользователя (виден в списке Users)
3. В **SQL Editor** выполните (замените `<UID>` и ФИО на свои):

   ```sql
   insert into profiles (id, full_name, role)
   values ('<UID>', 'Ваше Имя Фамилия', 'general_director');
   ```

   Этот запрос выполняется от имени администратора БД в SQL Editor,
   поэтому RLS ему не мешает. Дальше этот пользователь (как гендир)
   уже может через интерфейс приложения (раздел "Пользователи")
   заводить остальных сотрудников и назначать им роли — SQL вручную
   для всех последующих пользователей уже не нужен, только для самого
   первого.

### Учётная запись "разработчик" (владелец платформы)

Роль `developer` (см. миграцию `0012_developer_role.sql`) заводится ТОЧНО
ТЕМ ЖЕ способом, что и первый гендир выше (Dashboard → Add user → скопировать
UID → SQL insert в `profiles`, только с `role = 'developer'`) — и только так:
через интерфейс приложения создать пользователя с этой ролью нельзя
(её нет в списке ролей формы "Пользователи"). У `developer` те же права,
что у `general_director`/`technical_director`, и сверх того — правка
структуры оргсхемы; при этом сам профиль-разработчик НЕВИДИМ для
гендира/техдира (не отдаётся им ни в списке пользователей, ни где-либо
ещё — см. RLS в 0012), поэтому и заводить его нужно только с ведома
владельца платформы, отдельным email/паролем.

### Как это работает технически (без backend)

Создание пользователя через интерфейс использует обычный публичный
`supabase.auth.signUp()` (доступен с publishable key), но на отдельном,
изолированном клиенте — чтобы не потерять сессию того, кто создаёт
пользователя (см. `src/lib/supabaseAuxClient.ts`). Реальная защита —
не сокрытие кнопки, а RLS: "голая" учётная запись без строки в
`profiles` не даёт никакого доступа к данным, а создать профиль с
ролью может только `general_director`/`technical_director`.

Если в Supabase включено подтверждение email (Authentication → Providers
→ Email → Confirm email), новый сотрудник не сможет войти, пока не
подтвердит адрес письмом — для внутреннего рабочего инструмента обычно
удобнее отключить это требование в настройках проекта.

## Структура

- `profiles` — роль и ФИО, 1:1 с `auth.users`
- `sites` — участки работ
- `drilling_tasks` (+ `drilling_task_diameters`) — задания на бурение
- `core_description_tasks` (+ `core_description_external_diameters`) —
  задания на описание керна: своя скважина (`drilling_task_id`) или
  скважина подрядчика (`external_*` поля)
- `reports` (+ `report_costs`) — посменные сводки. Суточная сводка
  отдельно не хранится — считается на фронтенде агрегацией посменных
  за дату (см. ТЗ v0.7)
- `drilling_organizations`, `cost_categories` — справочники

Подробная бизнес-логика — см. ТЗ (актуальная версия v0.7) в переписке
с заказчиком.
